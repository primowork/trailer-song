# סורק קאברים מאושרים — IFPI Israel

אפליקציית Streamlit למציאת קאברים אפיים (trailer covers) ולבדיקה האם הם מיוצגים
במאגר הפדרציה הישראלית לתקליטים וקלטות.

## מבנה

| קובץ | תפקיד |
|---|---|
| `app.py` | ממשק Streamlit: מסך אחד לחיפוש, מדידה ובדיקת רפרטואר |
| `covers.py` | גילוי קאברים לפי יצירה (SecondHandSongs, ובנפילה לאחור MusicBrainz) |
| `search.py` | חיפוש ב-iTunes ו-Deezer, מיזוג, ניפוי כפילויות ודירוג רלוונטיות |
| `federation.py` | בדיקת רפרטואר מול ifpi.co.il (מסלול HTTP מהיר + נפילה ל-Playwright) |
| `audio.py` | תרגום מדדי האודיו לציון גודל 0..100 (פונקציה טהורה) |
| `components/audio_meter/` | מדידת האודיו עצמה, ב-Web Audio API בדפדפן של המשתמש |
| `suggest.py` | השלמת שמות שירים ותיקון שגיאות כתיב מול הקטלוג |
| `artists.py` | רשימת האמנים הגדולים בכל הזמנים (בילבורד), כנקודת פתיחה לחיפוש |
| `charts.py` | מצעדים חיים וקטגוריות מ-Deezer, עם קאש |
| `billboard.py` | פרסר לעמוד מצעד בילבורד שמור, לייבוא ידני |
| `preview.py` | משיכת בייטים של preview בשרת, כמעקף לחסימת CORS |
| `storage.py` | אחסון מתמיד: רשימה שחורה, קאש אימותים, סטטוסים |

## הרצה מקומית

```bash
pip install -r requirements-dev.txt
playwright install chromium
streamlit run app.py
pytest -q
```

## משתני סביבה

| משתנה | ברירת מחדל | תיאור |
|---|---|---|
| `TRAILER_SONG_DATA_DIR` | `/data` ואם לא ניתן לכתיבה — `.data/` מקומי | תיקיית אחסון הנתונים |
| `PORT` | `8501` | הפורט שעליו רץ Streamlit (Railway מזריק אוטומטית) |
| `IFPI_SEARCH_URL` | `https://www.ifpi.co.il/search.asp` | דף חיפוש הרפרטואר |
| `IFPI_ARTIST_FIELD` / `IFPI_TRACK_FIELD` | זיהוי אוטומטי | כפיית שמות שדות הטופס |
| `IFPI_PROXY` | ריק | ניתוב הבקשות לפדרציה דרך proxy, כשהאתר אינו נגיש מהשרת |
| `SHS_API_TOKEN` | ריק | טוקן ל-SecondHandSongs, אם נדרש |
| `MUSICBRAINZ_USER_AGENT` | `trailer-song/2.0 (...)` | MusicBrainz דורש User-Agent מזהה |

## איך החיפוש עובד

כל חיפוש מתרחב לכמה שאילתות (הגולמית + וריאציות כמו `trailer cover`, `epic cover`,
`cinematic cover`), רצות במקביל מול iTunes בשלושה קטלוגים (US/GB/DE) ומול Deezer,
ואז מתמזגות. שיר שמופיע בכמה אלבומים או בשני המקורות מזוהה כרשומה אחת לפי
`track_key` (שם אמן ושיר מנוקים), והתוצאות מדורגות לפי התאמה לשאילתה + סימני
"קאבר אפי" (מילות מפתח, ז'אנר, ורשימת אמנים מובילים ב-`EPIC_SEEDS`).

סימון "הצג רק תוצאות שלא ראיתי" מעביר לחיפוש את מפתחות השירים שכבר הוצגו, כך
שלחיצה חוזרת מביאה חומר חדש.

## נורמליזציה ודירוג

`normalize_title` מאחדת ווריאציות ניסוח של אותו שיר: אפוסטרוף (`Dreamin'` → `Dreaming`)
וסמן פסקול (`- From "San Andreas"`). היא מוסיפה `g` רק אחרי אפוסטרוף ולעולם לא מורידה
`g` קיים, כך ש-`Sing` ו-`Bring Me To Life` אינם נפגעים. בלעדיה `California Dreaming`
שהמשתמש מקליד ו-`California Dreamin'` שהוא השם האמיתי הפיקו מפתחות שונים, וכל שרשרת
ההתאמה נשברה.

`score_track` היא `relevance + min(epic_bonus, 30)`: רלוונטיות לשאילתה היא המרכיב
הראשי, וסימני "אפיות" הם תוספת חסומה. קודם הבונוסים נצברו ללא תקרה, וטראק דחוס במילות
מפתח ניצח התאמה אמיתית.

## סימני טריילר

`covers.trailer_signal` מחזירה אילו סימנים קושרים הקלטה לעולם הטריילרים: בית הפקה
(`EPIC_SEEDS`), אמן קאברים מוכר (`TRAILER_COVER_ARTISTS`), שיבוץ בפסקול (`From "..."`),
ז'אנר, או מילת מפתח. שתי הרשימות נפרדות בכוונה: `EPIC_SEEDS` הן חברות מוזיקת טריילרים,
בעוד שהארכיטיפ הנפוץ יותר הוא אמן מיינסטרים שעשה קאבר לשיר ישן עבור טריילר. הצ'קבוקס
בממשק מקדם גרסאות עם סימן ואינו מסתיר גרסאות בלעדיו.

## גילוי קאברים

הלשונית "מצא קאברים לשיר" שואלת מאגר קאברים **יחסי** במקום לנחש מכותרות. חיפוש טקסט
מוצא קאבר רק אם מישהו כתב בכותרת שלו את שם השיר המקורי plus מילה כמו "trailer";
קאבר בשם אחר בלתי נראה. `covers.py` מאתר את היצירה המקורית ואז מושך את כל הביצועים
שלה, ומעשיר כל אחד מול iTunes/Deezer כדי לקבל preview ואורך.

מקור ראשי SecondHandSongs, נפילה לאחור MusicBrainz (פתוח לגמרי, כיסוי נמוך יותר).
ביצוע שאינו בחנויות עדיין מוצג, בלי preview.

## בדיקת רפרטואר הפדרציה

היעד הוא `ifpi.co.il/search.asp` ("רפרטואר הפדרציה"). **הערה חשובה:** גרסאות עד
ספטמבר 2026 פנו ל-`federation.co.il`, שהוא ארגון אחר לגמרי (הפדרציה לקניין רוחני
ומלחמה בסחר בלתי חוקי). השדות `artName`/`trkName` ו-`CategoryID=94` נכתבו עבור אותו
אתר שגוי ולכן מעולם לא נמצאו. כל תוצאת אימות מלפני התיקון חסרת משמעות.

- **זיהוי שדות:** שמות שדות הטופס מזוהים מה-HTML בפועל מתוך רשימת מועמדים, וניתן
  לכפות אותם דרך משתני סביבה.
- **preflight:** בדיקה אחת לכל אצווה. אם הטופס לא זוהה, כל האצווה מסומנת `UNKNOWN`
  מיד. לפני כן שדה חסר עלה 30 שניות × 3 אסטרטגיות = 90 שניות לכל שיר.
- **מהירות:** דפדפן Chromium אחד לכל האצווה, ניסיון HTTP ישיר לפני הרמת דפדפן,
  וקאש תוצאות ל-30 יום.
- **דיוק:** התאמה דורשת גם שם אמן וגם שם שיר; המייצג נלקח מעמודת "מיוצג בפדרציה ע"י".
- **מבנה הדף:** לאתר אין `<table>` כלל — טבלת התוצאות בנויה מ-`div` צפים עם
  `class="om"` לכל שורה. הפרסור מזהה גם `<tr>` וגם את המבנה הזה. שמות שדות
  החיפוש האמיתיים הם `artist` ו-`song` (לא `artName`/`trkName`).
- **שלושה מצבים:** 🟢 ברפרטואר · 🔴 לא נמצא · 🟠 לא ידוע (הבדיקה נכשלה).

התוצאה היא **תג מידע ולא פילטר**, והסינון לפיה כבוי כברירת מחדל: `search.asp` הוא
רפרטואר השמעה ושידור, וקאברים אפיים מגיעים לרוב מספריות הפקה שאינן בו.

## כשהפדרציה אינה נגישה מהשרת

`ifpi.co.il` אינו נגיש מחלק מספקי הענן: הבקשות עושות timeout, כלומר לא מקבלות תשובה
כלל, בשונה מסירוב מנומס כמו 403. זו חסימה רשתית (חומת אש או חסימה גאוגרפית) ולא תקלת
קוד, ולכן אין מה לתקן בפרסור.

כפתור 🩺 "בדוק חיבור לפדרציה" בסרגל הצד מפריד בין השכבות ומדווח DNS, חיבור TCP, סטטוס
HTTP, זמן, ואילו שדות טופס זוהו:

| מה מוצג | מה זה אומר |
|---|---|
| `dns` נכשל | שם המארח לא נפתר |
| `tcp` נכשל אחרי ~10 שניות | האתר לא עונה מהרשת הזו — חסימה |
| `tcp` תקין אך `http_status` נכשל | מגיעים לשרת, והבעיה בשכבת HTTP |
| `artist_field` / `track_field` = "לא נמצא" | הדף נטען אך מבנה הטופס שונה מהמצופה |

כשהאתר חסום, שתי הדרכים הן להגדיר `IFPI_PROXY` לכתובת proxy שכן מגיע אליו (חל גם על
httpx וגם על Playwright), או להריץ את האפליקציה מרשת שממנה האתר נגיש. שאר המערכת —
חיפוש, גילוי קאברים, מדידת גודל — עובדת ללא תלות בפדרציה.

## איך מזוהה קאבר לטריילר

**לא לפי רשימות שמות.** גרסאות קודמות בדקו אם שם האמן מופיע ברשימת חברות הפקה או
אם הכותרת מכילה מילים כמו "epic". זה שאל "האם זה *נראה* טריילרי", לא "האם זה שימש
בטריילר", והמטא-דאטה של iTunes ו-MusicBrainz לא מתעדת שימוש בטריילר בשום שדה. שום
כיול של הרשימות לא היה יכול לעבוד.

במקום זה שני מנגנונים:

### 1. מדידת גודל, אוטומטית, בדפדפן

"מפוצץ אפי" מול "רגוע וקטן" היא תכונה של הטראק עצמו, ולכן היא נמדדת מוחלטת ולא
מול מקור: מדידה יחסית דרשה preview לשני הצדדים, ועל שירים ישנים הבסיס פשוט חסר.

המדידה רצה **אצל המשתמש** ב-Web Audio API (`components/audio_meter/index.html`),
אוטומטית על כל התוצאות המוצגות, ומחזירה ארבעה מספרים גולמיים.
`audio.bigness` מתרגם אותם לציון אחד:

| מדד | משמעות | משקל | רצפה → ניקוד מלא |
|---|---|---|---|
| `loudness` | RMS על כל הדגימות, בלי חיתוך | 35 | 0.08 → 0.30 |
| `low_end` | אנרגיה מתחת ל-120Hz חלקי האנרגיה ב-120–2000Hz | 30 | 0.8 → 3.0 |
| `onset_rate` | מכות לשנייה | 20 | 0.8 → 3.5 |
| `dynamic_span` | 10% החלונות החזקים חלקי 25% החלשים | 15 | 1.5 → 6.0 |

לכל מדד יש **רצפה**, כי לכל טראק ממוסטר יש כבר עוצמה ובס מסוימים; בלעדיה גם בלדה
אקוסטית אוספת ניקוד על עצם היותה מוקלטת. מעל 60 הטראק מסומן 🔊, מתחת ל-35 🌙,
ומה שביניהם 🎚️ ולא מוכרע. המיון נקבע לפי הציון.

**שני מדדים תוקנו אחרי שהנתונים הפריכו אותם.** הגרסה הראשונה מדדה בס כ-
`rms(lowpass)/rms(full)` וקשת כ-`max|x|/rms`, עם ספי ניקוד מלא של 0.45 ו-3.0.
בשטח הערכים היו 0.89–1.00 ו-5.6–7.7, כלומר **45 מ-100 הנקודות היו קבועות לכל
טראק** ו-`light version` קיבל 68 מול 69 של `Epic Trailer Version`. הבס תוקן ליחס
בין שתי רצועות (יחס לסך הכל נדבק ל-1 כי ספקטרום המוזיקה נשלט מהנמוכים ממילא),
והקשת הוחלפה בפריסה על פני הזמן במקום חדות טרנזיינט שנשלטת על ידי המאסטרינג.

הטווחים הנוכחיים הם עדיין הערכה. כפתור **⬇️ ייצא מדדים** מוריד CSV עם המספרים
הגולמיים ועמודת `label` ריקה — מילוי שלה ב"ענק"/"רגוע" הופך את הכיול הבא לנתונים.

הפענוח בדפדפן חוסך את `librosa` לגמרי — אין numba/llvmlite ואין מאות MB בתמונה.

**"לא נמדד" אינו "קטן".** טראק בלי preview, או ששרת ה-preview שלו חוסם CORS,
מוצג `⚪ טרם נמדד` עם הסיבה, ויורד לתחתית המיון במקום לקבל אפס.

### 2. ראיה לשימוש בפועל

`youtube.py` מחפש עדות שהשיר באמת שימש בטריילר, ומחזיר את הראיה עצמה — כותרת סרטון,
ערוץ וקישור — כדי שתשפוט בעצמך. הוא מבחין בין שימוש אמיתי לסגנון: `Official Trailer
Music` נספר, `Epic orchestral cover` לא.

מכסת YouTube היא 10,000 יחידות ליום וחיפוש עולה 100, כלומר **100 חיפושים ביום**.
לכן שאילתה אחת לכל יצירה וקאש ל-30 יום. בלי `YOUTUBE_API_KEY` השכבה כבויה ושאר
המערכת עובדת.

### מגבלות

- ה-preview הוא 30 שניות מתוך השיר. iTunes דוגם בדרך כלל מהאמצע, אבל אין ערובה
  שהדרופ נכלל: זו מדידה על מדגם
- `decodeAudioData` דורש CORS מהשרת שמארח את ה-preview. נגינה עובדת בלעדיו, פענוח לא.
  כשהחנות חוסמת, הרכיב מדווח `cors_failed` והמערכת נופלת אוטומטית למעקף: `preview.py`
  מושך את הבייטים בשרת ומגיש אותם כ-data URI, והפענוח נשאר בדפדפן. המעקף רץ
  בקבוצות של ארבעה כי כל preview עובר דרך הדף, וכל טראק מנוסה בו פעם אחת בלבד
- המשקלים והרצפות הם ניחוש ראשוני מושכל; המספרים הגולמיים מוצגים כדי לכייל אותם

## כשהפדרציה חסומה מהשרת: בדיקה ידנית דרך הדפדפן

`ifpi.co.il` חוסם IP-ים של דאטה-סנטרים: מהדיפלוימנט חיבור TCP עושה timeout אחרי 10
שניות, בעוד שהאתר נטען רגיל מדפדפן ביתי. אין לזה תיקון בקוד. שלוש דרכים לעקוף:

1. **הרצה מקומית** — `streamlit run app.py` על מחשב שממנו האתר נגיש. הכל עובד אוטומטית,
   בלי שום הגדרה. הדרך הפשוטה ביותר.
2. **`IFPI_PROXY`** — ניתוב דרך proxy שמגיע לאתר.
3. **בדיקה ידנית דרך הדפדפן** — מסלול מובנה בסרגל הצד, לשמירת הדיפלוימנט בענן שימושי:

| שלב | מה עושים | מה הקוד עושה |
|---|---|---|
| פעם אחת | פותחים את `search.asp`, מעתיקים את ה-HTML ומדביקים | `learn_fields_from_html` מזהה את שמות שדות הטופס האמיתיים ושומרת אותם. אם אף שם מוכר לא נמצא, מוצגת רשימת כל שדות הקלט לבחירה ידנית |
| לכל שיר | לוחצים 🔗 ליד השיר | `build_search_url` פותח את החיפוש בדפדפן עם האמן והשיר ממולאים |
| חזרה | מדביקים את ה-HTML של עמוד התוצאות | `verify_from_html` מריצה את אותה `parse_ifpi_table` ושומרת בקאש — הסטטוס זהה לאימות אוטומטי, כולל בייצוא ל-CSV |

כשה-preflight נכשל, כפתורי הבדיקה האוטומטית מוסתרים כדי לא לבזבז 20 שניות על ניסיון
שידוע שייכשל, והמסלול הידני מוצג במקומם.

## חיפוש קאברים לפי אמן

`covers.find_artist_covers` עונה על "מה הקאברים הגדולים שעשו לשירים של הלהקה הזאת",
בלי לדעת מראש איזה שיר. שני שלבים:

1. **אילו שירים הם שלו** — `artist_top_titles` מושכת 200 תוצאות לשם האמן, מסננת
   להתאמת שם, ומדרגת לפי **מספר ההופעות בקטלוג**: להיט חוזר על עשרות אוספים
   ו"best of", שיר עמוק מהאלבום מופיע פעם או פעמיים. מדד היכרות בלי API נוסף
2. **קאברים לכל אחד** — `find_epic_versions` הקיימת לשמונת השירים במקביל, מיזוג
   דרך `dedupe`, ותיוג כל תוצאה ב-`origin_track` כדי שיהיה ברור לאיזה שיר הקאבר

ייחודיות ה-uid נאכפת שם ולא בתצוגה: אותו קאבר יכול לחזור משני שירים, ומפתח widget
כפול מפיל את העמוד כולו.

## אינדקס המצעדים

פאנל `📇 אינדקס מצעדים` הוא נקודת הפתיחה לחיפוש: לחיצה על **אמן** מריצה חיפוש
קאברים לשירים שלו, לחיצה על **שיר** מריצה חיפוש גרסאות טריילר לשיר עצמו. המיקום
במצעד אינו משפיע על דירוג התוצאות — שם קובע מה שנמדד מהאודיו.

שלושה מקורות:

1. **מצעד Deezer חי** (`charts.py`) — קטגוריות ומצעדי שירים ואמנים, בלי מפתח.
   הבחירה ב-Deezer אינה שרירותית: `api.deezer.com` הוא המארח שהאפליקציה כבר מדברת
   איתו בכל חיפוש, ולכן מצעד ממנו יעבוד בדיפלוימנט. מקור שלא נבדק בסביבה שבה הוא
   ירוץ הוא הימור. הקאש הוא שש שעות להצלחה וחמש דקות לכישלון — תוכן `expander`
   ב-Streamlit מרונדר גם כשהוא סגור, ובלי קאש שלילי כל rerun היה משלם ניסיונות
   חוזרים על קריאה שנופלת
2. **רשימת בילבורד המובנית** (`artists.py`) — 125 האמנים הגדולים, בלי רשת
3. **מצעדים מיובאים** (`billboard.py`) — כל עמוד מצעד של בילבורד שנשמר מהדפדפן

### למה בילבורד מיובא ולא נגרד

ל-billboard.com אין API ציבורי, הגרידה נוגדת את תנאי השימוש שלהם, והם חוסמים
IP-ים של דאטה-סנטרים — בדיוק הכשל של `ifpi.co.il`, שבו פיצ'ר "עובד מקומית" נופל
בדיפלוימנט. מהסביבה שבה נכתב הקוד האתר חסום לחלוטין, כלומר אי אפשר היה אפילו
לבדוק גרידה.

לכן הייבוא עובר דרך הדפדפן של המשתמש, שבו העמוד ממילא נטען: שמירת העמוד והעלאתו
בסרגל הצד. פרסר אחד מכסה את כל המצעדים כי כולם חולקים את אותו מבנה — הדירוג הוא
ה-`c-label` הראשון בשורה, הכותרת היא ה-`h3`, והשדה שאחריה הוא האמן. מצעד אמנים
מזוהה בכך שהשדה הזה חוזר על הכותרת, ברוב השורות ולא בכולן: בעמוד האמיתי שורה אחת
מתוך 125 כתובה `JAY-Z` מול `Jay-Z`.

## רשימת האמנים הגדולים

`artists.py` מחזיק את דירוג "Greatest of All Time Artists" של בילבורד (125 שמות,
בסדר המקורי). בממשק זו רשימה מסוננת שלחיצה על שם בה ממלאת את שדה האמן ומריצה
מיד חיפוש קאברים.

זו נקודת התחלה ולא מדד: הרשימה סטטית, והדירוג בתוך התוצאות נקבע ממה שנמדד
מהאודיו ולא מהמיקום בה.

**כפתור לא יכול לכתוב לשדה שמעליו.** Streamlit אוסר על שינוי `session_state` של
widget אחרי שהוא נוצר, ולכן `queue_fields` שומרת את הערך ומחילה אותו בתחילת הריצה
הבאה, לפני שהשדות נוצרים. שתי זרימות נשברו על זה בשקט (כפתורי ההשלמה ורשימת
האמנים), ולכן `tests/test_app_flows.py` בודק אותן מקצה לקצה.

## "עוד כמו זה"

לכל שורה יש כפתור `🔁 עוד` עם שתי פעולות:

- **🎼 עוד קאברים לשיר הזה** — `more_covers_of` לוקחת את `origin_track` כשהוא ידוע,
  ואחרת מנקה את הכותרת (`Yellow (Epic Trailer Version)` ← `Yellow`) ומריצה את
  החיפוש האפי על השיר המקורי
- **🎨 עוד באותו סגנון** — `more_like_style` מחפשת לפי הז'אנר והאמן של הטראק.
  זו שכנות ולא המלצה: אין כאן מודל טעם. המדידה בדפדפן ממיינת את מה שחוזר לפי
  גודל, כך שהרשימה מתכנסת למה שנשמע גדול ולא רק למה שמתויג דומה

## כישלון רשת אינו "לא נמצאו תוצאות"

`search.get_json` הוא שכבת ה-HTTP המשותפת: שלושה ניסיונות עם השהיה גדלה על
429/500/502/503/504 ועל שגיאות רשת, בלי ניסיון חוזר על סטטוס קבוע כמו 404.
כישלון סופי מחזיר `None` — להבדיל מ-`{}` — ונרשם ב-`last_errors`.

זו הייתה תקלה אמיתית: `_mb_get` החזירה `None` בשקט על כל סטטוס שאינו 200,
ו-MusicBrainz מחזיר 503 על חריגת קצב באופן שגרתי. התוצאה נראתה בדיוק כמו "היצירה
לא במאגר", ולכן הלחיצה הראשונה "לא מצאה" והשנייה כן. עכשיו הממשק מבדיל: כשאין
תוצאות **וגם** נרשם כישלון, מוצגת שגיאה עם הסיבה במקום "לא נמצאו תוצאות".

## השלמת שמות ותיקון שגיאות כתיב

שם שיר משובש או חלקי מחזיר מעט מאוד תוצאות, והמשתמש לא יודע אם השיר לא קיים או
שהוא פשוט טעה. `suggest.py` פותר את שתי תקלות הקלט הנפוצות:

- **שגיאת כתיב או שם חלקי** — `bitter sweet symph` מציע את `Bitter Sweet Symphony`.
  ההצעות אינן מילון: הן שמות שחזרו מ-iTunes, כלומר שירים שקיימים במאגר שבו נחפש
  בפועל, ולכן לחיצה על הצעה מבטיחה שאילתה שתחזיר משהו
- **פריסת מקלדת עברית** — הקלדת שם באנגלית כשהמקלדת בעברית מייצרת ג'יבריש.
  `fix_layout` הופך אותו לפי מפת המקשים (`'ןמאקר` ← `winter`); זו תקלה
  דטרמיניסטית ולכן ההיפוך מדויק ולא מנחש. שני הנוסחים נשלחים לחיפוש והטוב מנצח

`did_you_mean` מציע תיקון רק כשההצעה קרובה מספיק להיות אותו שיר (מעל 65) ורחוקה
מספיק להיות תיקון בכלל (מתחת ל-96) — אחרת היינו מציעים למשתמש את מה שכבר הקליד.

## חיפוש: אמן מקור, ז'אנרים וטריות

- **אמן מקור** — שדה נפרד בחיפוש החופשי. מוסיף שאילתות כמו `<אמן> cover` כדי למצוא
  קאברים לשירים של אמן מסוים, ולא רק את מילת החיפוש
- **24 סגנונות** במקום ארבעה, כולם מונחים שמחזירים חומר שונה כשהם נוספים לשאילתה
- **פילטר חדשות** — השנה האחרונה / שנתיים / חמש שנים, לפי `releaseDate` מ-iTunes.
  תוצאה בלי שנה ידועה אינה נמחקת
- **`prefer_new`** — בונוס טריות שיורד מ-25 לאפס על פני חמש שנים, כך שחומר חדש עם ציון
  גבוה עולה מעל ישן באותו ציון
- **מיון** לפי גודל נמדד (ברירת מחדל), ציון, חדשים קודם, אורך או אמן
